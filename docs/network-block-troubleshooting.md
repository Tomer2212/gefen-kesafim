# מדריך: "לא ניתן להתחבר לשרת" — חסימה ברשת האינטרנט של המשתמש

מדריך זה מיועד לצוות התמיכה ולמשתמשי הקצה, למקרים שבהם משתמש **מחובר למערכת**
(רואה את השם שלו, מצליח להתחבר) אבל **תוכן לא נטען** ומופיעה הודעה כמו:

> "לא הצלחנו להגיע לשרת" / "לא ניתן להתחבר לשרת" / `Network Error` / `ERR_FAILED` /
> `blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present`

---

## 1. איך מזהים שזה המקרה הזה (ולא תקלת שרת אמיתית)

סימנים אופייניים — **כולם יחד**:

- אצל **משתמשים אחרים** באותו ארגון הכול עובד באותו רגע.
- אצל אותו משתמש, **מעבר לרשת אחרת פותר מיד** (נקודה חמה מהנייד / דאטה סלולרית).
- ב-DevTools (F12) → **Console** מופיעה שגיאת `CORS` / `ERR_FAILED` על בקשות
  לכתובת `gefen-kesafim-api.onrender.com`, למרות שהאתר עצמו (`gefenai.co.il`) נטען.
- אתרים אחרים באינטרנט נטענים אצל המשתמש כרגיל.

אם התמונה הזו מתקיימת — **הבעיה אינה בשרת של גפן AI**. השרת מוגדר נכון ושולח את
כל הכותרות הנדרשות. משהו **בנתיב הרשת של המשתמש** מסיר או חוסם את התשובות.

### מה גורם לזה

- ראוטר ביתי עם "הגנת אינטרנט" / בקרת הורים / סינון תוכן מובנה (נפוץ בראוטרים של ספקי אינטרנט).
- שרת DNS מסנן (למשל DNS "משפחתי" או חוסם-פרסומות) שתופס תת-דומיינים של `onrender.com`.
- אנטי-וירוס / חבילת אבטחה עם **"סריקת HTTPS" / "SSL scanning" / "Web Shield"**
  (Kaspersky, ESET, Avast, AVG, Bitdefender, Norton וכו').
- VPN, פרוקסי ארגוני, או חומת אש.
- רשתות WiFi ציבוריות / מלונות / מוסדות.

---

## 2. בדיקה מהירה למשתמש (2 דקות) — לאבחון

1. **החלפת רשת:** לחבר את המחשב לנקודה חמה מהטלפון (או דאטה סלולרית) ולנסות שוב.
   - עובד ברשת אחרת → הבעיה ברשת/ראוטר/ספק/אנטי-וירוס של המשתמש. המשך לסעיף 3.
   - לא עובד גם ברשת אחרת → ייתכן בעיה אחרת; אסוף פרטים (סעיף 5) ופנה לתמיכה.

---

## 3. פתרונות למשתמש — לפי סדר, מהקל לכבד

בצעו אחד-אחד ובדקו אחרי כל שלב אם המערכת נטענת.

### שלב א' — לשלול את הדפדפן

- לנסות **חלון גלישה בסתר (Incognito)**.
- אם בסתר עובד → תוסף דפדפן חוסם. להיכנס להגדרות התוספים, לכבות אותם, ולהדליק
  אחד-אחד עד שמאתרים את האשם (בד"כ חוסם פרסומות / תוסף פרטיות / תוסף אבטחה).
- לנסות **דפדפן אחר** (Chrome / Edge / Firefox).

### שלב ב' — לכבות VPN / פרוקסי

- לכבות כל VPN פעיל ולנסות שוב.
- ב-Windows: הגדרות → רשת ואינטרנט → פרוקסי → לוודא ש"זיהוי אוטומטי" בלבד ואין
  שרת פרוקסי ידני מוגדר.

### שלב ג' — אנטי-וירוס / חבילת אבטחה

- להשהות זמנית את **"הגנת הרשת" / "Web protection" / "סריקת HTTPS"** באנטי-וירוס
  (לא את כל האנטי-וירוס — רק את מודול הגלישה/HTTPS), ולנסות שוב.
- אם זה פתר → **לא להשאיר את ההגנה כבויה.** במקום זה, להוסיף לרשימת החריגים
  (Exclusions / Trusted sites) של האנטי-וירוס את הדומיינים מסעיף 6, ולהדליק את
  ההגנה מחדש.

### שלב ד' — להחליף DNS

אם רשת אחרת עבדה אבל לא רוצים להישאר על סלולרי — ייתכן שה-DNS של הרשת/הראוטר מסנן.

- **ב-Windows** (למכשיר בודד): הגדרות → רשת ואינטרנט → מאפייני החיבור → שרתי DNS →
  עריכה → ידני → IPv4 מופעל → DNS מועדף `1.1.1.1`, חלופי `8.8.8.8` → שמירה.
- לנסות שוב. אם עבד — זו הייתה סינון DNS.
- לתיקון קבוע לכל הבית — לשנות את אותו הדבר בהגדרות הראוטר (שרתי DNS ב-DHCP).

### שלב ה' — הגדרות הראוטר הביתי

- להיכנס לממשק הראוטר (בד"כ `192.168.1.1` או `192.168.0.1`).
- לחפש מודול בשם "Security" / "אבטחה" / "Web Protection" / "בקרת הורים" /
  "סינון תוכן" / "Firewall" — ולכבות אותו זמנית לבדיקה, או להוסיף את הדומיינים
  מסעיף 6 לרשימת ההיתר (Allow / Whitelist).
- בראוטרים של חלק מהספקים המודול הזה מנוהל מאפליקציה של הספק (לא מממשק הראוטר).

### שלב ו' — פנייה לספק האינטרנט

אם שום דבר לא עזר והבעיה רק ברשת הביתית — לפנות לתמיכת הספק ולבקש **לשחרר חסימה
לדומיינים** מסעיף 6. יש תבנית מוכנה בסעיף 7.

## 4. מה המערכת עצמה תציג עכשיו

לאחר העדכון האחרון, כשהמערכת לא מצליחה להגיע לשרת היא מנסה לזהות את הסיבה ומציגה
הודעה מדויקת יותר:

| מצב | הודעה שתוצג |
|---|---|
| אין אינטרנט במכשיר | "אין חיבור לאינטרנט במכשיר שלך" |
| השרת איטי / לא מגיב בזמן | "השרת לא הגיב בזמן — ייתכן עומס זמני" |
| השרת מגיב אך הרשת חוסמת חלק מהתקשורת | "השרת פעיל, אך רשת האינטרנט שלך חוסמת חלק מהתקשורת... פנו לספק" |
| השרת לא מגיב כלל | "לא ניתן להגיע לשרת כרגע... נסו רשת אחרת" |
| תקלת שרת אמיתית | "שגיאה בשרת (5xx) — נסו לרענן" |

ההודעה "השרת פעיל, אך רשת האינטרנט שלך חוסמת..." = כמעט תמיד המקרה של המדריך הזה.

## 5. מה לאסוף אם פונים לתמיכה

1. צילום מסך של **DevTools → Console** (F12) בזמן שהתקלה קורית.
2. צילום מסך של **DevTools → Network** — ללחוץ על השורה האדומה ולצלם את
   ה-Status וה-Headers.
3. באיזו רשת זה קרה (בית / משרד / ציבורי) והאם ברשת אחרת זה עבד.
4. שם ספק האינטרנט ודגם הראוטר.
5. שם תוכנת האנטי-וירוס / האבטחה המותקנת.
6. מערכת הפעלה ודפדפן (כולל אם זה מחשב מנוהל על ידי ארגון).

```

www.gefenai.co.il
```

**אין** לבצע "סריקת HTTPS / SSL inspection" על הדומיינים הללו — יש להוסיף אותם
לרשימת החריגים של הסריקה.

## 8. הסבר טכני קצר (לצוות)

הדפדפן שולח לפני כל בקשה מאומתת בקשת **preflight** מסוג `OPTIONS`. השרת מחזיר לה
כותרת `Access-Control-Allow-Origin: https://gefenai.co.il`. אם רכיב רשת בדרך
(פרוקסי-שקוף של ספק, אנטי-וירוס שמפרק TLS, ראוטר עם סינון) מסיר את הכותרת או מחזיר
דף שגיאה משלו — הדפדפן חוסם את הבקשה ומדווח "No 'Access-Control-Allow-Origin'
header is present", למרות שהשרת דווקא כן שלח אותה. אימות ישיר מול השרת
(`curl -i -X OPTIONS https://gefen-kesafim-api.onrender.com/schools/notifications
-H "Origin: https://gefenai.co.il" -H "Access-Control-Request-Method: GET"`)
מראה שהכותרת מוחזרת כשורה — כלומר הבעיה בנתיב, לא בשרת.
